# پلن تکمیل بردهای تک‌به‌تک کامپوننت‌های NOVA

## هدف

برای هر کامپوننت تصویریِ واقعی در storefront و پنل ادمین، یک هدف مستقل در فهرست مرکزی و یک بسته‌ی طراحی جدا بسازم. این مرحله فقط طراحی و مستندات طراحی است؛ کد محصول و رفتار برنامه تغییر نمی‌کند.

## وضعیت مبنا

- مبنای بررسی: `main` در commit `6e4770d05ca67b2fecd337298359de8c6d838176`؛ ۳۱۸ فایل TSX غیرتستی از web، admin و shared UI بررسی شده‌اند.
- ۲۰۳ نماد JSX پیدا شده‌اند. ۸ مورد فقط provider/router یا composition بدون ظاهر مستقل‌اند و با دلیل در `component-source-inventory.json` می‌مانند؛ آن‌ها زیر بردهای صفحه‌ی موجود پوشش داده می‌شوند.
- پوشش مستقل هدف: ۱۹۵ کامپوننت تصویری، شامل ۱۲ نماد با برد دقیق موجود و ۱۸۳ برد تازه.
- شناسه‌ها یکتا هستند و hash همه‌ی ۲۰۳ فایل منبع با snapshot مبنا تطبیق دارد. نتیجه‌ی coverage graph برای مسیرهای `apps/web/src` و `apps/admin/src` فایل‌های test و type را کنار گذاشته؛ فایل‌های منبع UI مستقیماً برای این فهرست مبنا قرار گرفته‌اند.

## محدوده و مالکیت

- منبع هدف‌ها: خروجی‌های تصویری/React در apps/web/src، apps/admin/src و packages/ui/src، با تطبیق مستقیم تعریف‌ها و وابستگی‌ها در فایل‌های منبع.
- هر symbol تصویری شناسه و ردیف مستقل می‌گیرد؛ اگر یک فایل چند کامپوننت تصویری دارد، هرکدام جدا ثبت می‌شوند.
- route/pageهای از پیش طراحی‌شده همچنان به برد صفحه‌ی مربوط پیوند می‌خورند؛ برد مستقل فقط برای خود کامپوننت و stateهای متعلق به آن ساخته می‌شود.
- helper، hook، formatter، validator، API، provider و wrapperهای بدون UI مستقل برد نمی‌گیرند؛ با مسیر و دلیل در فهرست exclusions ثبت می‌شوند تا شمارش شفاف بماند.
- بسته‌های ۱۵گانه‌ی موجود حفظ می‌شوند. هم‌پوشانی یک بسته‌ی موجود با چند source symbol، جای برد جداگانه‌ی سایر symbolها را نمی‌گیرد.

## معیار پذیرش

1. فهرست source شامل هر هدف مستقل، مسیر/تعریف دقیق، حوزه‌ی storefront/admin، وضعیت برد و دلیل هر مورد کنارگذاشته‌شده باشد.
2. برای هر هدف تصویری یک بسته‌ی مستقل با برد بصری، clean reference، مشخصات طراحی و handoff ساخته شود؛ state فقط وقتی نمایش داده شود که در منبع وجود دارد یا به‌وضوح به‌عنوان پیشنهاد علامت خورده باشد.
3. مقادیر و تعامل‌های source-defined از proposalها جدا باشند؛ RTL، حالت‌های responsive، focus/disabled/error/loading و مجوز assetها در صورت کاربرد ثبت شوند.
4. docs/designs/components/README.md برای همه‌ی هدف‌ها جدول وضعیت تک‌به‌تک داشته باشد و docs/project-status.md شمارش و محدودیت‌های واقعی طراحی را بازتاب دهد.
5. بررسی بصری با فایل‌های خروجی واقعی انجام شود. این کار تست یا پیاده‌سازی محصول محسوب نمی‌شود.

## مراحل

1. بازبینی فهرست کاندیداها با منبع فعلی main؛ جداسازی ۸ wrapper غیرقابل‌طراحی و ثبت دلیل پوشش آن‌ها در بردهای صفحه.
2. نگاشت پکیج‌های طراحی موجود به symbolهای دقیق؛ جلوگیری از پکیج تکراری.
3. ساخت بسته‌های مستقل و بردهای خوانا برای هر هدفِ باقی‌مانده، با اولویت گروه‌های منسجم وب و ادمین و حفظ شناسه‌ی پایدار.
4. بازبینی لینک‌ها، تعداد هدف‌ها، وجود فایل‌ها، source anchors، RTL و وضوح خروجی‌ها؛ سپس به‌روزرسانی فهرست مرکزی و snapshot وضعیت پروژه.
5. بازبینی diff و ثبت commit و PR مطابق روند مخزن.

## ریسک و محدودیت

- تعداد و مرز کامپوننت‌ها باید از UI واقعی تعیین شود، نه صرفاً شمارش فایل‌ها یا نام تابع‌ها.
- جزئیات اندازه‌گیری‌شده فقط وقتی ثبت می‌شوند که از منبع یا خروجی اندازه‌گیری‌شده پشتیبانی داشته باشند؛ بقیه با PROPOSED یا UNVERIFIED مشخص می‌شوند.
- اجرای تعاملی محصول، بارگذاری فونت‌های غایب، مجوز assetهای ناشناخته و CI نهایی شواهد جدا هستند و به‌عنوان تأیید طراحی ادعا نمی‌شوند.
