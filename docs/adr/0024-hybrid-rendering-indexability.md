# ADR-0024: Hybrid rendering and indexability foundation

Status: Accepted for SEO-001.

## Context

The storefront is a Vite + React client with hash routes. A browser fragment is
not sent to the server, so it cannot provide useful route-specific initial HTML
to a crawler. The existing API already owns catalog truth, published content,
and the public `GET /v1/seo/resolve` metadata/redirect boundary. Replacing the
client routing stack or introducing a new framework would create unnecessary
scope and migration risk.

## Decision

The web build produces its existing browser bundle plus a small Node-compatible
SSR/server entry. The server owns only the document boundary and crawler
responses. It recognizes these clean public aliases:

- `/` for home;
- `/category/:audience` for the existing women, men, and children category
  routes;
- `/product/:slug` for published catalog products; and
- `/content/:slug` for published content pages.

Each eligible public request, including an unrecognized legacy public path,
resolves `/v1/seo/resolve?path=...` first. A resolver redirect becomes the HTTP
redirect response. Otherwise the server reads the public catalog/content
endpoint required by the recognized route, combines that result with resolver
metadata, and emits one canonical URL, title, description, robots directive,
Open Graph set, and optional JSON-LD block. Private and system/asset paths
bypass the resolver and remain excluded or noindex. Product, category, home,
and content JSON-LD is derived from the public response; persisted structured
data takes precedence for non-product routes when the resolver supplies it.
Product JSON-LD is the exception: resolver metadata may provide scalar SEO
fields, but its unconstrained `structuredData` value cannot replace the
catalog-derived `Product`, `BreadcrumbList`, and `Organization` graph. The
visible product title, price, description, availability, breadcrumbs, and real
media therefore remain the source of truth for that graph. HTML and JSON
contexts are escaped before insertion.

The server emits a small useful initial body containing the route heading,
description, and safe product/content links. When the root carries the
`data-nova-ssr="true"` marker, its body is wrapped in a
`data-nova-ssr-shell="true"` child. The client captures that shell's inner HTML
and hydrates a static handoff component whose first render reproduces the same
marker and HTML through `dangerouslySetInnerHTML`; its `useEffect` then swaps
to the interactive App. An unmarked client-only root continues through the
`createRoot` fallback, so the handcrafted server body is never hydrated as the
different App tree. The bundle starts with an injected internal hash route
(`#product/...`, `#category/...`, or `#content/...`) and keeps the current
hash-router interaction model. The new `#content/:slug` route reads the
published content endpoint and renders plain text/body blocks; it does not
render arbitrary HTML.

Private, account, auth, admin, cart, checkout, order, and return paths are
never in the sitemap and receive `noindex, nofollow` metadata. System and asset
paths are excluded from resolver lookup and receive noindex behavior when the
web server handles them. Unknown and unpublished public resources receive a
noindex 404. Resolver/catalog/content failures receive a noindex 503 response
so an outage cannot create indexable empty pages. Client-side metadata updates
upsert the same managed tags and remove stale canonical/JSON-LD nodes,
preventing duplicate hydration metadata. Ordinary public compatibility hash
routes for home, category, product, and published content remain index/follow;
search, product-list/filter/sort, temporary-state, private, error, and system
routes are noindex.

`/robots.txt` is generated by the server with explicit private-path exclusions.
`/sitemap.xml` is generated from public catalog categories, products, and the
published-only `GET /v1/content/pages` summary list. Candidates are recognized
by the same clean-route parser used by the renderer, and each candidate is
passed through the SEO resolver before it is included; `noIndex` metadata and
redirects are omitted. This prevents category, product, or content slugs that
render 404 or are not indexable from being advertised. The content endpoint
returns only sitemap-safe slug/title/updatedAt fields, so drafts and bodies do
not enter crawler generation. A failure in any source or resolver lookup fails
the sitemap closed with a non-cacheable 503 response; an optional deployment
manifest is not used as a substitute for API truth.

## Cache and deployment assumptions

Successful public HTML uses `public, s-maxage=60,
stale-while-revalidate=300`. Successful sitemap responses use five minutes of
shared freshness and fifteen minutes of stale-while-revalidate. Redirects are
cacheable for five minutes. Private, 404, 503, and crawler-error responses use
`no-store`. The reverse proxy/CDN must honor these headers and route clean
public paths, `/robots.txt`, and `/sitemap.xml` to the web server. The standard
Vite client build must run before the SSR build; production starts
`apps/web/dist/ssr/server.mjs` with `NOVA_API_ORIGIN` and the public
`NOVA_WEB_ORIGIN` configured. The API must be reachable from the web process.
Catalog product image data is used as-is: no intrinsic dimensions are invented
because `CatalogProduct` does not provide them. The existing
`.product-detail__main-image` `4 / 5` aspect-ratio reserves the primary image
box; an image URL gets eager loading with asynchronous decoding, while a
missing image URL renders a neutral reserved box and no JSON-LD image value.

Hash URLs remain supported for existing bookmarks and in-app navigation. They
are not treated as the canonical crawler URLs; clean aliases are the indexable
boundary.

## Consequences

SEO-001 provides useful route-specific initial HTML without moving commerce
logic, catalog/content ownership, or client routing into the web server. The
tradeoff is a small server deployment requirement and a dependency on the
complete published-content summary endpoint for content sitemap discovery. If
that endpoint or any SEO resolver lookup fails, the server returns a
non-cacheable 503 instead of emitting a partial sitemap. No live API, database,
browser, CDN, or crawler validation is implied by the focused tests.
